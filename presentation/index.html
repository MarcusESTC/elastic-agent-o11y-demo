The Problem

AI Agents Are
Black Boxes

❓ No Visibility

You know the user sent a message and got a reply. Everything in between — model calls, latency, token usage, errors — is invisible.

💸 Cost Blindness

Token costs accumulate silently. No per-request breakdown, no alerting on unexpected spend spikes, no user-level attribution.

🐛 Hard to Debug

When the agent gives a bad answer, there's no trace to follow. No correlated logs, no replay, no span waterfall showing where time was spent.

📊 No SLOs

You can't set latency or error-rate SLOs on something you can't measure. Customers feel the pain before you do.

Logs

Correlated
Structured Logs

Every turn emits two log records via the OTel LoggerProvider. They carry the active trace_id automatically — click any log in Kibana to jump straight to the trace waterfall.

  • Logs ship via OTLP to the APM server endpoint → logs-generic.otel-default
  • trace_id + span_id injected by OTel LoggingHandler — zero extra code
  • Structured fields: tokens, latency_ms, cost_usd, model, conversation_id
  • Visible in Kibana Observability → Logs + APM → Logs tab

Implementation

One SDK,
Three Signals

The full OTel pipeline is ~50 lines of Python. Standard SDK — no Elastic-specific client code. Any OTel-compatible backend would work.

  • TraceProvider → SimpleSpanProcessor → OTLPSpanExporter
  • MeterProvider → PeriodicExportingMetricReader → OTLPMetricExporter
  • LoggerProvider → SimpleLogRecordProcessor → OTLPLogExporter
  • Single Resource block shared across all three providers
  • Full-path OTLP endpoints — no URL mangling
opentelemetry-sdk otlp-proto-http no vendor lock-in 
# Traces → ingest endpoint
trace_exporter = OTLPSpanExporter(
    endpoint=f"{INGEST}/v1/traces",
    headers=OTLP_HEADERS)
trace_provider = TracerProvider(resource=resource)
trace_provider.add_span_processor(
    SimpleSpanProcessor(trace_exporter))

# Metrics → ingest endpoint
metric_exporter = OTLPMetricExporter(
    endpoint=f"{INGEST}/v1/metrics",
    headers=OTLP_HEADERS)
reader = PeriodicExportingMetricReader(
    metric_exporter, export_interval_millis=30000)
meter_provider = MeterProvider(
    resource=resource, metric_readers=[reader])

# Logs → APM server endpoint
log_exporter = OTLPLogExporter(
    endpoint=f"{APM}/v1/logs",
    headers=OTLP_HEADERS)
log_provider = LoggerProvider(resource=resource)
log_provider.add_log_record_processor(
    SimpleLogRecordProcessor(log_exporter))

# Bridge Python logging → OTel
logger = logging.getLogger(SVC_NAME)
logger.addHandler(LoggingHandler(
    logger_provider=log_provider))

Key Takeaways

Why Elastic for
AI Observability

🏆 100% Sampling

Every single agent interaction is captured and stored. No sampling gaps, no missing traces during a customer demo, no "where did that request go?" moments.

🔗 Three-Signal Correlation

Traces, logs, and metrics share the same trace_id. Click a slow metric → jump to the log → jump to the trace waterfall — all in Kibana, zero pivoting between tools.

📐 OTel Native

gen_ai.* semantic conventions, OTLP/HTTP protocol, standard SDK. No vendor lock-in. The same instrumentation works with any OTel-compatible backend.

💡 Request / Response Storage

Full prompt and completion text stored as span events — no truncation. Every conversation is replayable and searchable via ES|QL directly in Kibana.

💰 Cost Visibility

Per-request token counts and cost_usd logged with every turn. Aggregate by user, model, or time window to understand and control AI spend.

⚡ Zero Extra Infra

One Python server, one OTel SDK, one OTLP endpoint. No collector sidecar, no extra agents, no additional services. Works in Docker or bare metal.

Step-by-step demo flow for a 10-minute customer session.

  • Open the Chat UI at http://localhost:5601. Point out the live OTel telemetry sidebar — signals, model, transport.
  • Send a message: "What is ES|QL?" Watch the trace ID, token count, latency, and cost appear instantly below the response.
  • Open APM → Services → gemini-demo-agent → Transactions → click invoke_agent. Show the trace waterfall with the two-span hierarchy.
  • Click the CLIENT span → Attributes tab → show gen_ai.* fields. Click Events tab → show the full prompt + completion text.
  • Service Map tab → show the arrow from gemini-demo-agent to google_gemini with latency on the edge.
  • Logs tab → show correlated log records. Highlight the shared trace_id linking log → trace.
  • ES|QL: query traces-generic.otel-default to show all conversations, ranked by token cost.
